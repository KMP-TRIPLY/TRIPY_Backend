# TRIPY 서비스 흐름

충청권 사적을 걸으며 미션을 푸는 스토리텔링 여행 게임. 코드에 실제로 구현된 것만 적었고,
기획 결정이 필요한 지점과 아직 비어 있는 연결을 함께 표시했다.

기준: 2026-09-02 · 도메인 9 · 컨트롤러 16 · 엔드포인트 41 · 엔티티 49 · 운영 방 36 · 관광 스팟 1004

---

## 1. 서비스가 두 갈래로 나뉘어 있다

TRIPY 는 성격이 다른 두 흐름을 담고 있다. 하나는 여행을 계획하는 일정 관리,
다른 하나는 코스를 돌며 미션을 푸는 게임이다.

```
흐름 A — 여행 계획                        흐름 B — 미션 게임
─────────────────────                    ─────────────────────
소셜 로그인 (카카오/네이버/구글)            코스 고르기 (로그인 없이도 조회)
      ↓                                        ↓
여행 성향 프로필 입력                       게임방 만들기 (공개)
      ↓                                        ↓
여행(Trip) 만들기 · 제목 · 기간             참여 / 시작 (방장이 시작)
      ↓                                        ↓
장소(Place) 추가 · 좌표 · 방문일 · 메모      스팟 도착 → 미션 제출
      ↓                                        ↓
대시보드 · D-Day · 추천 명소                종료 → 랭킹 → 리워드 정산
```

> **연결이 없다.**
> `Trip`·`Place` 는 `Course`·`GameRoom` 을 참조하지 않고, 그 반대도 없다.
> 사용자가 만든 여행 일정에 코스를 담을 수 없고, 게임을 끝내도 그 기록이 여행 일정에 남지 않는다.
> 두 기능을 각각 쓰는 별개 앱처럼 동작한다. **이 문서의 가장 큰 기획 공백이다.**

## 2. 도메인 지도

| 도메인 | 담당 |
|---|---|
| `user` | 소셜 로그인, JWT, 리프레시 토큰, 여행 성향 프로필 |
| `trip` | 여행 일정. 제목과 기간만 갖는다 |
| `place` | 여행에 담는 장소. 좌표·방문일·메모 |
| `course` | 코스 → 스팟 → 미션. 스토리텔링 콘텐츠의 뼈대 |
| `game` | 게임방, 진행상황, 미션 제출 이력. 가장 큰 도메인 (55 파일) |
| `tourism` | 관광공사 API 2종, 응답 캐시, 관광지 1004건 |
| `main` | 대시보드와 D-Day. 두 흐름을 한 화면에 모은다 |
| `ranking` | 방 안 실시간 순위, 코스별 최종 순위 |
| `reward` | 쿠폰·리워드 정산. 게임 종료와 따로 돈다 |

## 3. 게임 한 판의 생애주기

순서가 곧 상태 전이다. 방은 `WAITING → RUNNING → FINISHED` 를 한 방향으로만 지나간다.

### 01. 코스를 고른다
로그인 없이 볼 수 있다. 코스 상세에는 스팟과 미션이 들어 있지만 **정답은 빠져 있다.**
```
GET /api/courses · /api/courses/{courseId} · /api/courses/regions
```

### 02. 방을 만든다
만든 사람이 **방장**이 된다. 비밀번호도 방 코드도 쓰지 않는다 — 대기 중인 방은 목록에 공개된다.
정원을 1로 두면 혼자 하는 방(`SOLO`)이 되어 아무도 들어올 수 없다.
```
POST /api/game-rooms   { courseId, roomName, maxMembers }
```

### 03. 사람들이 들어온다
목록에서 방을 골라 `roomId` 로 참여한다. **팀을 고르지 않는다** — 한 방이 한 팀이다.
이미 이 방 멤버라면 새로 넣지 않고 원래 자리로 되돌린다(재입장).
```
GET  /api/game-rooms              (대기 중인 방 목록)
POST /api/game-rooms/{roomId}/join (본문 없음)
```

### 04. 방장이 시작한다
시작·코스 변경·강퇴·종료는 모두 방장만 할 수 있다. 그리고 **방장은 방을 나갈 수 없다.**
```
POST /api/game-rooms/start
```

### 05. 스팟에 도착해 인증한다
GPS 좌표를 보내면 반경 안인지 확인하고, 스팟 순서를 지켰는지도 검사한다.
통과하면 그 스팟의 미션이 열린다.
```
POST /api/game-rooms/{roomId}/spots/{spotId}/arrive   { lat, lng }
```

### 06. 미션을 푼다
퀴즈는 서버가 채점한다. 사진 계열(PHOTO·AR·VOICE)은 **이미지 업로드 전용 경로로만** 받는다 —
문자열만 보내면 통과하던 구멍이 있었다. 힌트를 먼저 보면 감점이 예약된다.
```
POST /api/missions/{missionId}/submit · /hint · /photo?roomId=
```

### 07. 중간에 나가면
대기 중이라면 기록 없이 빠진다 — 마음이 바뀌면 다시 들어올 수 있다.
진행 중에 나가면 사유가 남고 그때까지의 점수는 방에 보존되며, **그 방에는 다시 못 들어온다.**
앱이 꺼져서 튕긴 것과 스스로 나간 것은 하차 이력으로 구분한다.
```
POST /api/game-rooms/{roomId}/leave   { reasonType, reasonDetail }
```

### 08. 방장이 끝낸다
점수가 잠기고 `rankings` 에 방 기록과 멤버별 기록이 쌓인다. 이게 코스 랭킹의 재료가 된다.
```
POST /api/game-rooms/{id}/end
```

### 09. 리워드를 정산한다
종료와 **별개로 수동 호출**해야 한다. 순위에 따라 쿠폰을 발급하고,
하차한 사람의 점수를 남은 멤버에게 재분배한 리포트를 만든다.
```
POST /api/rewards/settle   { gameRoomId }
```

## 4. 순위는 두 층으로 본다

| 범위 | 무엇을 비교하나 | 엔드포인트 |
|---|---|---|
| 방 안 | 멤버끼리 개인 점수 (실시간, 진행 중인 방만) | `GET /api/rankings/live?gameRoomId=` |
| 코스 | 같은 코스를 돈 **방끼리** 최종 점수 | `GET /api/rankings/courses/{id}?mode=ROOM` |
| 코스 | 같은 코스를 돈 개인끼리 최종 점수 | `GET /api/rankings/courses/{id}?mode=PERSONAL` |

한 방이 한 팀이므로 방 안에서 겨룰 상대는 같은 방 멤버뿐이다.
방과 방의 경쟁은 코스 랭킹에서 일어난다. 코스가 곧 "게임 한 종류"라서 순위가 게임별로 나뉜다.

## 5. 외부 의존 — 관광공사 API 두 종

둘은 성격도 ID 체계도 다르다. 하나는 통계, 하나는 콘텐츠다.

| API | 주는 것 | 쓰이는 곳 | 상태 |
|---|---|---|---|
| `LocgoHubTarService1`<br>`areaBasedList1` | 방문자 인기 순위, 이름, 좌표, 분류.<br>**사진·설명은 없다** (필드 11개) | 대시보드 추천 명소, 관광지 목록 | 정상 |
| `KorService2`<br>`locationBasedList2` | 사진(`firstimage`), 주소, 전화, 분류 | 주변 명소 조회, 추천 명소 사진 매칭 | 정상<br>(2026-09-02 활용신청 승인) |

두 API 의 ID 가 다르다. 통계 쪽은 32자 해시(`hubTatsCd`), 콘텐츠 쪽은 숫자(`contentid`)라
ID 로 이어붙일 수 없다. 그래서 사진은 **좌표 주변을 조회해 이름이 정확히 일치하는 곳**에서 가져온다 —
거리순 1위를 쓰면 엉뚱한 사진이 붙는다(국립공주박물관 좌표에서 222m 지점이 선화당).
못 찾으면 사진 없이 둔다.

캐시: 시군구별 응답을 24시간 보관. 빈 결과는 캐싱하지 않는다 —
한 번 비면 원인을 고쳐도 하루 동안 비어 보인다.

## 6. 기획 결정이 필요한 것

코드로는 답이 나오지 않는 것들이다. 위에서부터 영향이 큰 순서다.

### 6.1 여행 계획과 게임을 이을까
지금은 완전히 분리돼 있다. 여행 일정에 코스를 담거나, 게임 결과를 여행 기록으로 남기거나,
코스를 돌 날짜를 일정에 넣는 것이 전부 불가능하다.

**물어야 할 것:** 여행 일정이 게임의 상위 개념인가, 아니면 둘은 끝까지 별개 기능인가?

### 6.2 추천을 개인화할까
대시보드 추천은 **충청·대전·세종 10개 시군구 고정**이다. 사용자가 누구든 같은 곳이 나온다.
여행 성향 프로필(역사·힐링·미식·액티비티·감성 5개 점수, 이동수단, 동행유형)이 이미 있는데
추천에 쓰이지 않는다.

**물어야 할 것:** 성향·여행 지역 기반 추천으로 갈 것인가? 그러면 5개 점수를 무엇으로 채우나?

### 6.3 성향 점수는 누가 올리나
`UserTravelProfile` 의 5개 점수는 사용자가 직접 입력할 때만 바뀐다.
게임을 몇 판 하든, 어떤 미션을 풀든 점수에 반영되지 않는다. 코드에 갱신 지점이 없다.

**물어야 할 것:** 미션 종류·방문 스팟으로 성향을 자동 갱신할 것인가, 설문 결과로만 둘 것인가?

### 6.4 서비스 지역을 넓힐까
코스는 충남(`44`) 것만 있고, 관광 데이터는 10개 시군구가 코드에 상수로 박혀 있다.
코스 생성은 이제 전국 도시명을 받지만 관광 데이터는 따라오지 않는다.

**물어야 할 것:** 충청권 특화로 갈 것인가, 전국인가? 후자면 시군구 목록을 설정이나 DB로 옮겨야 한다.

### 6.5 정산을 자동으로 돌릴까
게임을 끝내도 쿠폰이 나가지 않는다. `POST /api/rewards/settle` 을 따로 불러야 한다.
지금은 누가 언제 부르는지 정해져 있지 않다.

**물어야 할 것:** 종료 시 자동 정산인가, 운영자가 확인 후 수동인가?

### 6.6 방장이 사라지면 어떻게 하나
방장은 나갈 수 없지만 앱을 끄면 서버는 알 수 없다. 그러면 방을 시작하거나 끝낼 사람이 없어
남은 멤버가 진행 중인 방에 갇힌다. 방장 위임도, 자동 종료도 없다.

**물어야 할 것:** 방장 위임을 만들까, 일정 시간 뒤 자동 종료로 갈까?

## 7. 손봐야 하는 것

결정보다 실행에 가까운 항목들이다.

### 7.1 [보안] 정산·쿠폰 발급에 권한 검사가 없다
`POST /api/rewards/settle` 과 `POST /api/rewards/coupons` 는 로그인만 하면 누구나 부를 수 있다.
남의 게임을 정산하거나 임의의 사용자에게 쿠폰을 발급할 수 있다.
`Role` 열거형(USER·ADMIN)이 있고 인증 주체에 `ROLE_*` 권한도 실려 있지만,
코드 어디에도 `hasRole`·`@PreAuthorize` 가 없다.

**할 일:** 두 엔드포인트를 ADMIN 으로 제한. 관리자 계정을 어떻게 만들지도 같이 정해야 한다.

### 7.2 [보안] 쿠폰 재고에 잠금이 없다
발급 한도를 세는 것과 실제 발급 사이가 벌어져 있어, 두 방이 동시에 정산하면 한도를 넘겨 발급될 수 있다.

**할 일:** 발급 시 비관적 잠금 또는 카운트에 유니크 제약.

### 7.3 [기술 부채] teams 테이블이 방과 1:1 로 남아 있다
한 방 = 한 팀으로 바꿨지만 `teams` 테이블은 지우지 않았다. 점수·진행상황 컬럼이 여기 붙어 있고
reward·ranking 도메인이 이 테이블을 참조한다. API 에서는 팀이 보이지 않는다.

**할 일:** 흡수하려면 점수 컬럼 이전과 FK 4개 마이그레이션이 필요하다. 급하지 않다.

### 7.4 [죽은 코드] 참조가 0인 엔티티가 세 벌 있다
`Leaderboard`(기간별 리더보드), `Notification`(알림), `WeatherCache`(날씨) —
테이블 정의와 열거형만 있고 이를 읽거나 쓰는 코드가 없다. 만들려다 멈춘 기능의 흔적이다.

**물어야 할 것:** 만들 예정인가? 아니면 지울 것인가 — 남겨두면 다음 사람이 있는 기능으로 오해한다.

### 7.5 [운영] 스키마를 Hibernate 가 관리한다
`ddl-auto: update` 라 컬럼 추가는 자동이지만 삭제·이름변경은 안 된다.
마이그레이션 도구(Flyway 등)가 없어 스키마 변경이 손으로 실행하는 SQL 이다.
실제로 이번 전환에서 `rankings` 의 CHECK 제약에 막혀 한 번 실패했다.

**할 일:** 변경이 잦아지면 Flyway 도입. 지금은 `src/main/resources/db/` 에 SQL 을 남긴다.

## 8. 이번에 바꾼 것

| 주제 | 내용 |
|---|---|
| 한 방 = 한 팀 | 방장과 팀장이 겹쳐 있던 구조를 방장 하나로 통일. API 에서 팀 개념 제거, 플레이 경로를 `roomId` 기준으로 전환, 방 정원 검사 추가(이전에는 무제한 입장) |
| 코스 조회 | 로그인 없이 코스를 볼 수 있게 열었다. 읽기만 열고 생성·삭제는 인증 유지 |
| 지역 코드 | 코스 생성 시 도시 이름으로 시도 코드를 서버가 찾는다. 애매하면 400 으로 되돌려 틀린 코드를 넣지 않는다 |
| 추천 명소 | 매번 무작위로 섞이던 것을 인기순으로. 기준월 후행 문제와 빈 결과 캐싱 문제를 고쳐 빈 배열로 나오던 것도 해결. 사진도 붙였다 |
| 혼자 하기 | 정원 1명 방(SOLO)을 만들 수 있게 했다. 모드는 정원에서 유도해 어긋난 조합이 생기지 않는다 |
| 부수 수정 | 힌트 이력이 요청자가 아니라 팀장으로 기록되던 문제, `/v3/api-docs` 가 500 나던 라이브러리 충돌, 도달 불가 코드 제거 |

---

코드에서 확인한 사실만 담았고, 운영 서버와 DB 를 직접 조회해 검증했다.
엔드포인트별 상세는 `/v3/api-docs`, 게임방 도메인은 [docs/game-room.md](game-room.md) 를 보면 된다.
